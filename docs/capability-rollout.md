## 1. GitHub MCP — APPLIED (live user config, outside this repo)

* Server: user-scope `github` in the Claude Code user config (same URL as the plugin, so it replaces the plugin entry):
  `https://api.githubcopilot.com/mcp/`, headers `X-MCP-Readonly: true`, `X-MCP-Toolsets: repos,issues,pull_requests`,
  and a `headersHelper` that emits the `Authorization` header at connect time.
* Credential: a fine-grained, read-only PAT (Contents, Issues, Pull requests, Metadata) stored in a **macOS Keychain
  item** (`github-mcp-pat`). No credential value exists in any repository file, shell profile or MCP config. The helper
  is `~/.claude/bin/github-mcp-headers` (mode 0700).
* Effective exposure: 22 read tools (49 without the read-only header). Verified 2026-10-24: API auth, MCP connection,
  private-repo read, tool list.
* **Renewal** (token expires 2027-01-21): create a new fine-grained read-only PAT, then in a normal Terminal run
  `security add-generic-password -a "$USER" -s github-mcp-pat -U -w` and paste at the hidden prompt. No config change.
* Not exposed to Agent OS workers: the worker launcher supports command/args servers only, and GitHub MCP has no
  `launch`. `gh` (human identity, keyring) is a separate credential and is untouched.

## 6. Dispatched-worker GitHub isolation and fail-closed routing — APPLIED 2026-10-25 (protected + companion code)

* **Scope:** automatically dispatched Agent OS workers only. These are command-text deny patterns plus a launch-environment
  change: **defense in depth, not a sandbox.** They are passed per launch; nothing is written to any settings file, so
  interactive Claude Code, Codex and OpenCode (and your `gh` login and push workflow) are unaffected.
* `config/workers.yaml`: `gh` denied to Claude workers (`gh`, `env gh`, `/opt/homebrew/bin/gh`, `*gh auth*`, `*gh api*`;
  only forms verified against a real worker are listed), an explicit `withheld_executables: [gh]` for every worker, and
  (optional) the macOS `security` CLI denied to Claude workers.
* `agentos/workers.py`: workers launch with `GH_CONFIG_DIR` pointing at an empty `state/runtime/gh-isolated` and the five
  GitHub token variables blanked.
* **GitHub tasks fail closed.** `capability_policy.plan_for` (dispatch and `capabilities match`) plans a tool only if it is
  *deliverable* to the worker: an MCP needs a `launch` in `mcp.yaml`; a CLI listed in `withheld_executables` (or denied by
  pattern) is not. GitHub MCP has no launch (HTTP + `headersHelper`), so a `devops.github` task is `not_dispatched /
  blocked / human handoff` (reason `integration-undeliverable`) and `gh-cli` is never a fallback. The registry facts
  (and the frozen SystemOne datasets) are unchanged and GitHub MCP stays recorded healthy for interactive use.
* Codex has no MCP under Agent OS launch (intentional asymmetry); tasks needing `code.semantic_navigation`,
  `web.docs_lookup` or browser capabilities never select it (deterministic test).
* **Residual risk (documented, not hidden):** with an empty `gh` config dir `gh api`/`gh pr` fail, but `gh auth token` can
  still fall back to the OS keyring (an exit code was observed once; no credential was read), and any same-user process can
  in principle read a Keychain item. Claude worker patterns are best-effort text matching. One Codex run
  (`workspace-write`, 2026-10-25) showed no network, `gh` not logged in, and `security list-keychains` failing: an
  observation, not a guarantee. A Bash-enabled worker is not a hard secrets boundary.
